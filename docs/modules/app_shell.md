# CORE MODULE: App Shell (`lib/main.dart`, `lib/app/`)

Entry point through app startup: `main.dart`, `app/app.dart`, `app/router.dart`, `app/route_guard.dart`, `app/theme.dart`, `app/spacing.dart`. Also covers `lib/firebase_options.dart`, which `main.dart` consumes directly.

---

## `lib/main.dart` — the real entry point

- **Purpose**: Bootstraps Flutter, initializes Firebase (with a retry loop for a known web race condition), and mounts the app under Riverpod's `ProviderScope`.
- **Status**: IMPLEMENTED.
- **Flow**:
  1. `WidgetsFlutterBinding.ensureInitialized()`.
  2. `if (Firebase.apps.isEmpty) await _initializeFirebaseWithRetry();` — guarded because, per the inline comment, Flutter's web service-worker bootstrap can re-run `main()` a second time within the same page load (install-then-reload on a fresh origin), and re-registering the default Firebase app in a release build throws (re-creating an already-existing TrustedTypes policy) and leaves the page blank.
  3. `runApp(const ProviderScope(child: TaarakApp()));`
- **`_initializeFirebaseWithRetry()`**: up to 5 attempts, each calling `Firebase.initializeApp(options: DefaultFirebaseOptions.currentPlatform)`, with a linearly-increasing backoff (`400ms * attempt`) between attempts, rethrowing only on the final failed attempt. The comment cites a specific, still-open FlutterFire web bug (`firebase/flutterfire#9995`): in a minified release build, `Firebase.initializeApp()` can lose a race against the JS-side plugin registration finishing, throwing a `PlatformException(channel-error, ...)` and leaving the page blank; it "reliably succeeds a moment later," so retry-with-backoff is the documented standard workaround pending an upstream fix. Debug builds never hit this because they're slow enough for the JS side to already be ready.
- **Notable imports**: `firebase_core`, `flutter_riverpod`, `app/app.dart`, `firebase_options.dart`.
- **Depends on**: `TaarakApp`, `DefaultFirebaseOptions`.
- **Hardcoded/demo content**: none — this is genuine production bootstrap logic, not a stub.

## `lib/firebase_options.dart`

- **Purpose**: Generated by the FlutterFire CLI (`flutterfire configure`), providing `DefaultFirebaseOptions.currentPlatform`, which resolves to a platform-specific `FirebaseOptions` constant.
- **Status**: GENERATED — not hand-written; would be overwritten by re-running `flutterfire configure`.
- **Platforms configured**: **web** and **android** only. `currentPlatform` explicitly `throw`s `UnsupportedError` for any other `defaultTargetPlatform` (iOS, macOS, Windows, Linux) — so this app cannot initialize Firebase on those platforms as currently configured; a fresh `flutterfire configure` run targeting those platforms would be required first.
- **Project**: both platform configs point at Firebase project `taakrak-d9ed0` (per the `projectId` field and the file's own header comment).
- **Secrets note**: this file contains what look like real Firebase client API keys (`apiKey` values) for both the web and android configs. **SECRET PRESENT IN SOURCE — DO NOT COPY INTO DOCUMENTATION.** (The file's own header comment argues these are safe to commit because a Firebase *client* config only identifies which project to talk to — access is enforced by Firestore security rules and Firebase Auth, not by keeping this file secret — but per this handover's rule, the values themselves are not reproduced here regardless.)
- **Depended on by**: `main.dart` only.

## `lib/app/app.dart`

- **Purpose**: The `TaarakApp` root widget — decides between a splash screen (while session restore is in flight) and the fully-routed `MaterialApp.router`, and is the single place that keeps four app-lifetime Riverpod providers alive by watching them unconditionally on every build.
- **Status**: IMPLEMENTED.
- **Key classes/functions**:
  - `TaarakApp` (`ConsumerWidget`) — `build` does, in order:
    1. `ref.watch(syncOnReconnectTriggerProvider)` — keeps M17's reconnect-triggered sync alive for the app's lifetime, independent of which screen is on top (see `docs/modules/sync.md`).
    2. `ref.watch(syncPollingTriggerProvider)` — same lifetime, periodic sync (default 45s, admin-configurable).
    3. `ref.watch(notificationWatcherProvider)` — same lifetime; watches for new alerts/incidents and fires a local (client-only, no server push) notification, works while the app is open/backgrounded. (`lib/features/notifications/` is outside this documentation's assigned scope, noted here only because it's watched at the same root.)
    4. `ref.watch(rolePermissionOverridesProvider)` — same lifetime; the comment explains this keeps the role→permission override map "warm" so `computeRedirect`'s `ref.read` of it (inside the router's `redirect` closure, which cannot `ref.watch`) always sees a resolved value instead of a perpetually-reloading `autoDispose` provider with no watcher. (`lib/features/admin/` is likewise outside this scope, noted for the same reason.)
    5. Reads `authControllerProvider`'s `isLoading` via `.select` — while true, returns a bare `MaterialApp` showing `_SplashScreen` (no router at all). The comment states router redirects assume session restore is already resolved, so the app holds on a splash screen rather than teaching the router about a loading state.
    6. Once restore resolves, watches `appRouterProvider` and returns `MaterialApp.router` with `theme: AppTheme.light`, `darkTheme: AppTheme.dark`, `routerConfig: router`, `debugShowCheckedModeBanner: false`, `title: 'TAARAK'`.
  - `_SplashScreen` (private `StatelessWidget`) — centered "TAARAK" text plus a `CircularProgressIndicator`, no branding beyond the wordmark.
- **Notable imports**: `flutter_riverpod`, `app/router.dart`, `app/theme.dart`, and cross-feature imports into `features/admin/`, `features/auth/`, `features/notifications/`, `features/sync/` — this file is the app's literal composition root for lifetime-scoped providers, so cross-feature coupling here is structural, not incidental.
- **Depends on**: `appRouterProvider`, `AppTheme`, `authControllerProvider`, `syncOnReconnectTriggerProvider`, `syncPollingTriggerProvider`, `notificationWatcherProvider`, `rolePermissionOverridesProvider`.
- **Depended on by**: `main.dart` (the only place `TaarakApp` is constructed).
- **Root-level providers watched once at app startup — full list, confirmed from this file**: `syncOnReconnectTriggerProvider`, `syncPollingTriggerProvider`, `notificationWatcherProvider`, `rolePermissionOverridesProvider`, plus `authControllerProvider` (read via `.select`) and `appRouterProvider` (read once session restore resolves).

## `lib/app/router.dart`

- **Purpose**: Defines the app's single `GoRouter` instance (`appRouterProvider`) — every screen's route, the redirect hook into `route_guard.dart`'s pure decision function, and the Riverpod→`ChangeNotifier` bridge that makes an auth state change re-evaluate routing.
- **Status**: IMPLEMENTED.
- **Key classes/functions**:
  - `_RouterRefreshNotifier` (private `ChangeNotifier`) + `_routerRefreshProvider` (`Provider.autoDispose`) — `ref.listen(authControllerProvider, ...)` calls `notifier.notify()` on every auth-state change, bridged into GoRouter's `refreshListenable` so a login/logout re-evaluates the redirect without rebuilding the whole router.
  - `appRouterProvider` (`Provider<GoRouter>`) — only ever mounted once session restore has resolved (see `app.dart` above), so `redirect` never has to handle an in-flight loading state. No `initialLocation` override — comment notes go_router's own default reads the real browser URL on web (`Uri.base`), so a refresh or direct deep link lands correctly; `computeRedirect` gates it identically regardless of how the location was reached. `redirect` uses `ref.read` (not `watch`) for both the session and the permission overrides — the closure runs on every navigation attempt, not during the provider's own build; comment notes a permission-override edit takes effect on the affected user's *next* navigation, not as a live mid-page kick-out.

## `lib/app/route_guard.dart`

- **Purpose**: The pure, side-effect-free redirect decision function for the entire app — deliberately built with no `BuildContext`/`GoRouterState` dependency so it's unit-testable without pumping a widget tree.
- **Status**: IMPLEMENTED.
- **Key classes/functions**:
  - `_authRoutes` — `{'/login', '/register', '/forgot-password'}`.
  - `defaultRoutePermissions` — the `Map<String, Permission>` reproduced in full in the route table above (28 entries; `/`, `/profile`, and the three auth routes plus `/unauthorized` are absent from this map by design).
  - `dashboardIncidentDetailPrefix = '/dashboard/incidents/'`, `fieldIncidentDetailPrefix = '/field/incidents/'` — the two path-parameter routes need prefix matching since `defaultRoutePermissions` only does exact-location lookups.
  - `computeRedirect({session, location, routePermissions = defaultRoutePermissions, permissionOverrides}) -> String?`:
    1. **No session** (`session == null`): if `location` is one of the three auth routes, allow it (`null` = no redirect); otherwise force `/login`.
    2. **Has session, on an auth route**: redirect to `/`  — an authenticated user is never allowed to sit on login/register/forgot-password.
    3. **Permission check**: `required` = `Permission.monitorZones` if the location starts with the dashboard-incident-detail prefix, else `Permission.viewAssignedIncidents` if it starts with the field-incident-detail prefix, else whatever `routePermissions[location]` resolves to (which is `null` — no requirement — for any route not in the map, including `/`, `/profile`, `/unauthorized`, and the auth routes reached with a session already established via step 2's redirect).
    4. If a permission **is** required: `effectivePermissions` = `permissionOverrides?.effectivePermissionsFor(session.user.role) ?? session.user.role.permissions` — an admin-configured per-role override (from `features/admin/`) takes precedence over the role's baseline permission set when present. If `required` is not in `effectivePermissions`, redirect to `/unauthorized`.
    5. Otherwise, `null` — proceed to the requested location.
- **Notable imports**: `features/admin/domain/role_permission_overrides.dart`, `features/auth/domain/auth_session.dart`, `features/auth/domain/permission.dart`, `features/auth/domain/user_role.dart` — this file's only external coupling is to the auth/admin **domain** layer (types, not services), keeping the redirect logic itself dependency-light and testable.
- **Depends on**: `AuthSession`, `Permission`, `UserRole`, `RolePermissionOverrides` (types only).
- **Depended on by**: `router.dart`'s `appRouterProvider` (the only caller).

## `lib/app/theme.dart`

- **Purpose**: The single shared `ThemeData` (light + dark) every role's screens draw from — one theme for the whole app rather than per-feature theming, since every role reuses the same shell.
- **Status**: IMPLEMENTED.
- **Key classes/functions**: `AppTheme` (static-only) — `light`/`dark` getters, both built from `ColorScheme.fromSeed` off a shared `_seedColor` (`0xFF0B6B65`, a deep muted teal, chosen per its comment to read as "institutional/trustworthy" and to stay visually distinct from every severity/risk color so the brand color is never mistaken for a status indicator); `_themeFrom(scheme)` sets `useMaterial3: true` and per-component theme data for `AppBarTheme`, `CardThemeData` (rounded 12px, outlined, `Spacing.xs` vertical margin as a default gap between stacked cards), `ChipThemeData`, `FilledButtonThemeData`/`OutlinedButtonThemeData`/`TextButtonThemeData` (all rounded 10px), `InputDecorationTheme` (filled, rounded 10px, distinct enabled/focused/error border colors), `ListTileThemeData`, `DividerThemeData`, `SnackBarThemeData` (floating), `DialogThemeData`; `_textTheme(scheme)` — a deliberately defined type scale (weights/letter-spacing on `headlineSmall`/`titleLarge`/`titleMedium`/`titleSmall`/`labelLarge`/`labelSmall`, line-height 1.4 on body styles) layered onto `Typography.material2021().black`, explicitly **not** using `google_fonts` — the comment states this is deliberate: a network font dependency would be at odds with the app's offline-first purpose, and a bundled font asset would add bytes for no functional gain versus a defined type scale on the platform's own system font.
- **Depends on**: `app/spacing.dart` (for `Spacing.xs` in the card margin).
- **Depended on by**: `app.dart` (`AppTheme.light`/`AppTheme.dark` on both the splash `MaterialApp` and the routed `MaterialApp.router`).

## `lib/app/spacing.dart`

- **Purpose**: The app's spacing scale (4px base unit, matching Material's own grid) and named responsive breakpoints — both meant to replace ad hoc pixel values that made the UI feel inconsistent before this was introduced.
- **Status**: IMPLEMENTED.
- **Key classes/functions**: `Spacing` (static-only) — `xs=4, sm=8, md=16, lg=24, xl=32, xxl=48`; `Breakpoints` (static-only) — `tablet=700` (below this: single-column phone layout), `desktop=1100` (at/above this: full multi-column layout, e.g. the Command Dashboard's side-by-side panels).

## Startup sequence, end to end

1. `main()` initializes Flutter bindings, initializes Firebase (web/android only, with retry), then mounts `ProviderScope(child: TaarakApp())`.
2. `TaarakApp.build` unconditionally watches four app-lifetime providers (sync reconnect trigger, sync polling trigger, notification watcher, role-permission-overrides warmer) before anything route-related happens.
3. While `authControllerProvider`'s session restore is in flight, a bare `MaterialApp` shows `_SplashScreen` — no router exists yet.
4. Once restore resolves, `appRouterProvider` is built (a `GoRouter` whose `redirect` reads the now-resolved session synchronously) and `MaterialApp.router` takes over.
5. Every navigation — including the very first one — runs through `computeRedirect`: unauthenticated → `/login`; authenticated-on-an-auth-route → `/`; authenticated-but-missing-permission → `/unauthorized`; otherwise proceed.

## Known gaps / handover flags

- `firebase_options.dart` only configures **web and android** — iOS/macOS/Windows/Linux would throw `UnsupportedError` at `Firebase.initializeApp` time if this app were ever built for those targets without first re-running `flutterfire configure`.
- `/sms-prototype` and `/device-relay` are live, permission-gated routes (same permission as `/sos`) in every build — there is no route-level dev-mode gate despite `AppConfig.isDevMode` existing specifically to gate "dev-only convenience affordances" like these, per that field's own doc comment in `core/config/app_config.dart`.
- `route_guard.dart`'s permission check is entirely exact-path or fixed-prefix based; any future route with path parameters other than the two already special-cased (`/dashboard/incidents/:id`, `/field/incidents/:id`) would need its own prefix constant added here, or it will fall through to "no permission required."
