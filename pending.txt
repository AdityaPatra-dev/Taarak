TAARAK: real Firebase backend (Auth + Firestore), so devices actually connect
Context
Everything built so far runs against either mocked auth or a hand-rolled Dart backend stub (in-memory, resets on restart, only reachable if someone runs it on a laptop) — explicitly never meant to be the real thing. The user now wants a real, hosted backend so different devices/logins genuinely share data, plus real authentication, and asked specifically about Firebase.

Decision (confirmed with the user): full Firebase — Auth + Firestore, not a hybrid. Reasoning: Firestore's SDK already solves "different devices connect freely" (offline cache + sync) more robustly than the custom push/pull built this session, Firebase Auth gives real accounts (password reset etc.) for free, and there's no server to host or pay for. This replaces the backend/ stub and its HTTP transport — not the app's actual architecture. The local Drift cache stays the source of truth for reads; the sync engine's dedup/priority/conflict/backoff rules (lib/features/sync/application/sync_engine.dart) stay exactly as built — only the transport underneath swaps from HTTP to Firestore. This is a transport swap, not a rewrite of proven logic.

Scope boundary (deliberately not "sync everything"): only tables that represent genuinely shared, cross-device state get synced — local_incident_reports, local_incidents, local_hazard_zones, local_shelters, local_alerts, local_alert_acknowledgements. Tables that are pure derived computations from that shared data (risk/vulnerability/ capacity assessments, relocation plans, routes) stay local-only — each device recomputes them from synced inputs via the existing engines. Syncing those too would be real over-engineering for what's needed right now.

Out of scope for this plan (flagged, not forgotten): an admin UI to provision Field Responder/Official/Admin accounts. Until that exists, those roles get set by hand-editing the role field on a user's Firestore document — fine for now, a real gap for later.
